# 国际化（i18n）规范

覆盖两个项目：`blog`（Hugo 静态站）与 `blog-editor`（内容编辑器）。
本文描述**当前的实现**：两边各自怎么组织文案、语言怎么切换、构建阶段怎么按语言出页；
§10 把方案放回选型坐标里对比（对标 Astro / Hexo / Docusaurus），§11 是依赖与代码量账，
§12 是扩展到 N 种语言时的资源组织、切换机制与扩展流程，§13 是边界。
文中标注「实测」的结论都来自本仓库实际构建或接口调用的输出；
§10 与 §12.5 里关于其它框架 / 方案的结论来自各自官方文档与规范。

---

## 0. 范围

| 项目 | 国际化的部分 |
| --- | --- |
| `blog` | 站点界面文案、文章/页面/栏目页内容、站点设置、导航菜单 |
| `blog-editor` | 编辑器界面文案、后端返回给界面的消息、编辑器的内容读写 |

两边的**语言代码、key 命名、资源文件格式**共用同一套标准（第 5 节），
但**翻译文件各自独立**——它们描述的是不同的东西，没有可共用的条目。

## 1. 语言集合

| 项 | 取值 |
| --- | --- |
| 语言代码标准 | **BCP 47**（`zh-CN`、`en`），与 `hugo.toml` 的 `locale` 一致 |
| Hugo 的 `lang` 键 | **全小写**（`zh-cn`、`en`），只用于 URL 与配置键名 |
| 默认语言 | `zh-cn` |
| 起步语言 | `zh-cn`（默认）+ `en` |
| 扩展方式 | 博客：在 `[languages]` 加一块 + 建对应内容文件，**模板与代码不动**；编辑器：加一份 `static/i18n/<代码>.json`，再把语言代码加进 `app.py` 的 `LANGUAGES`（见 §3.4） |

**为什么是这两个**：站点内容、README、编辑器界面当前全是中文，作者是中文母语者，
英文是覆盖面最广的第二语言。数量本身不构成架构约束——方案按 N 种语言设计。

**大小写的分工不能混**（实测确认）：

| 项 | 取值 | 决定什么 |
| --- | --- | --- |
| `locale` | 规范大小写 `zh-CN` | `<html lang>`、`hreflang` |
| `[languages.<键名>]` | 全小写 `zh-cn` | 配置键名、URL 前缀的来源、内容文件后缀 |

**键名全小写是本项目的命名约定，不是 Hugo 的规则。** Hugo 官方文档里语言键遵循 RFC 5646，
示例本身就带区域（`[languages.en-US]`、`[languages.pt-BR]`）。实测：把键名改成 `[languages.zh-CN]`
并把 `defaultContentLanguage` 一起改成 `"zh-CN"`，产物与全小写时**逐字节相同**——URL 路径默认
会被转成小写（`disablePathToLower`），内容后缀的匹配也不区分大小写。统一小写是为了让键名、
URL 前缀、内容后缀、编辑器读到的语言代码保持同一种拼写。

**真正会坏的是 `defaultContentLanguage` 与键名对不上**（实测）：写成
`defaultContentLanguage = "zh-cn"` 配 `[languages.zh-CN]` 时，Hugo 不报任何警告，而默认语言会
**整块丢掉 `params`**——站点 description、作者简介、`displayName`（语言切换菜单变成空白）、
`dateFormat`（日期退回英文格式）一起失效。

`locale` 写错是另一类静默错：Hugo 找翻译文件不区分大小写，所以主题文案照样是中文，
只有 `hreflang` 悄悄变了样。

上面两条都由 `tools/check.py` 查——它们都不会让构建报错，只能靠检查兜住。

## 2. 需要国际化的内容

### 2.1 博客：内容

| 类型 | 位置 | 翻译方式 |
| --- | --- | --- |
| 文章 | `content/posts/<slug>/index.md` | 同目录 `index.<lang>.md` |
| 独立页面 | `content/about.md` | `about.<lang>.md` |
| 栏目页 | `content/posts/_index.md` | `_index.<lang>.md` |
| 首页 | `content/_index.md` | `_index.<lang>.md` |
| 分类/标签/合集页 | `content/tags/_index.md` 等 | `_index.<lang>.md` |

文章用 **page bundle + 语言后缀**（`index.md` / `index.en.md`），媒体文件两份共用，
URL 不变。这与编辑器现有的 bundle 约定一致，是它的自然延伸。

**taxonomy 页要单独建**：`tags`、`categories`、`series` 三个 taxonomy 列表页
默认由 Hugo 自动生成标题（中文站点会显示成英文的 `Tags`）。要本地化就必须
建 `content/tags/_index.md`（中文 title）+ `_index.en.md`（英文 title），
菜单文案才会跟着对（见 3.3）。

### 2.2 博客：界面与配置

| 类型 | 位置 | 说明 |
| --- | --- | --- |
| 主题界面文案 | 主题自带 `i18n/*.yaml`（36 种语言，中文 97 条 / 英文 98 条） | **不复制**，站点按需覆盖 |
| 站点自定义文案 | `i18n/<locale>.json` | 新增；也可覆盖主题同名 key |
| 站点标题/简介 | `hugo.toml` 的 `[languages.<lang>]` 与 `.params` | 每种语言一份 |
| 导航菜单文案 | **不写死**，由页面 title 驱动 | 见 3.3 |
| 站点设置（作者、社交链接） | `hugo.toml` 的 `[languages.<lang>.params]` | 不随语言变的可留在顶层 |

### 2.3 编辑器

| 类型 | 位置 | 承载方式 |
| --- | --- | --- |
| 界面静态文案 | `static/index.html` 的标记 | `data-i18n` / `data-i18n-ph` / `data-i18n-title` 三个属性指向 key |
| 界面动态文案 | `static/index.html` 的 `<script>` | 一律经 `t()` 取；后端给的对象经 `loc()` |
| 后端提示 | `app.py` 的 `msg()` | 返回 `{key, text, args}`，`text` 是中文兜底 |
| 后端错误 | `app.py` 的 `AppError` / `self.fail()` | 返回 `{error, code, args}`，前端查 `error.<code>` |
| 内容读写 | `app.py` 的文件路径逻辑 | 支持 `index.<lang>.md` |

**明确不进 i18n 的**：代码注释与 docstring、`_log()` 日志（开发者看的，中文更利于排查）。
这些是给维护者读的，翻译它们只会增加维护面。

「有没有漏」不靠数条目数，靠两个可复跑的检查脚本：
编辑器的 `check_i18n.py`（`python check_i18n.py`，纯读文件）校验两份表互相对齐、
代码引用的 key 都能查到、`app.py` 里出现的错误码都有文案、没有孤儿键；博客的 `tools/verify_i18n.py`
（先 `hugo` 构建、再运行）校验多语言产物：多语言改造前的中文 URL 一个不少、
语言标记与翻译关系正确。

## 3. 语言切换与默认语言

### 3.1 博客：URL 结构

```toml
defaultContentLanguage = "zh-cn"
defaultContentLanguageInSubdir = false   # 中文留在根路径
```

产物（实测）：

```
/posts/hello-world/          中文，URL 与上线现状完全一致
/en/posts/hello-world/       英文
/about/  /en/about/
```

**`defaultContentLanguageInSubdir` 必须是 `false`**：站点已上线，
`baseURL` 下的中文链接是既有事实，不能因为加语言而整体搬家。

副作用（实测）：Hugo 会自动生成 `/zh-cn/index.html`——一个指向 `/` 的
`meta refresh` 重定向页，以及 `/zh-cn/sitemap.xml`。前者由
`disableDefaultLanguageRedirect` 控制（Hugo 0.140.0 起；`defaultContentLanguageInSubdir`
为 `false` 时，它管的正是「语言子目录跳回根目录」这一个别名），canonical 指向根路径，无害；
后者是 sitemap 索引的组成部分（见 4.3），不是冗余。

### 3.2 博客：切换入口

**不用自己写组件**——主题已内置，无需任何配置：

- `layouts/partials/header/components/translations.html` 在 `.IsTranslated` 为真时
  自动出现在桌面菜单与移动菜单里，列出 `.AllTranslations`
- 每项显示的是 `[languages.<lang>.params] displayName`，**这个字段必填**，否则菜单项空白
- `head.html` 自动输出双向 `hreflang`（用 `locale` 值）
- 可选：`params.languageRedirect` 启用按浏览器语言/上次选择自动跳转
  （`storageKey` 默认 `blowfish_preferred_language`）

### 3.3 导航菜单：文案的单一来源

菜单项现在写成 `name = "文章"`，这是**页面标题的副本**——
`content/posts/_index.md` 的 `title` 已经是"文章"。两处描述同一件事，加语言时必然不同步。

主题模板取的是 `{{ .Name | markdownify }}`，不做 i18n。但 Hugo 在菜单项
**没有显式 `name`** 时用 `pageRef` 指向页面的 title 当菜单文案。所以：

```toml
[[menu.main]]
  pageRef = "posts"      # 不要 name
  weight = 10
```

实测效果：中文菜单「文章 / 关于」，英文菜单自动变成「Posts / About」。
**菜单文案的来源从此只有一处——页面自己的 title。**

### 3.4 编辑器：语言设置

编辑器里有**两个互不相干的「语言」**，不要混：

| 维度 | 含义 | 入口 | 取值来源 |
| --- | --- | --- | --- |
| 界面语言 | 编辑器自己的按钮、提示用哪种语言 | 页头语言选择器 | 编辑器自带的文案表（见 §5） |
| 内容语言 | 正在编辑的是哪一版文章 | 编辑器顶部的语言条 | 站点配置 `[languages]` |

界面语言：

| 项 | 约定 |
| --- | --- |
| 默认语言 | `zh-CN` |
| 记忆方式 | `localStorage`，键名 `blog-editor.language`（与主题的 `blowfish_preferred_language` 区分） |
| 首次访问 | 无记忆值时取浏览器语言，认不出的一律收敛到 `zh-CN` |
| 取文案 | `GET /api/i18n/<语言>`，返回**展平成点号键**的文案表 |

**可选语言由 `app.py` 的 `LANGUAGES` 决定**（当前 `zh-CN`、`en`）。选择器的选项来自文案表里的
`langs.*` 段——多放一份表就会多出一个选项，但后端仍按 `LANGUAGES` 归一化请求，不在名单里的
语言会被收敛回默认语言、拿到的是默认语言的表。所以加一种界面语言要动两处：加一份
`static/i18n/<代码>.json`，并把代码加进 `LANGUAGES`。

内容语言：

| 项 | 约定 |
| --- | --- |
| 传递方式 | 显式参数——`GET` 走 `?lang=`，`POST` 走请求体的 `lang` 字段 |
| 单语言站点 | 不传，也不显示语言条；行为与没有多语言时完全一致 |
| 未配置的语言 | 后端返回 `unknown_lang` 错误，不悄悄退回默认语言 |
| 站点没配多语言时 | `lang` 一律按 `None` 处理，字段路径落在配置顶层 |

后端只把语言用于**选文案和选文件**，不参与任何业务判断——语言不影响文章状态的算法。

## 4. 构建阶段的语言输出

### 4.1 每个语言独立渲染

Hugo 按 `[languages]` 逐语言渲染整站。内容文件的匹配规则是**文件名去掉语言后缀后相同**，
即 `hello-world.md` ↔ `hello-world.en.md`，bundle 则是 `index.md` ↔ `index.en.md`。
媒体文件不参与匹配，两份内容共用同目录的图片/视频。

### 4.2 自动产出的语言标记（实测）

| 产物 | 中文页 | 英文页 |
| --- | --- | --- |
| `<html lang>` | `zh-CN` | `en` |
| `hreflang` | 同时输出 `zh-CN` 与 `en` 两条，互相指向 | 同左 |

两边的 `hreflang` 是同一对，这是搜索引擎识别翻译关系的依据，无需手工维护。

### 4.3 sitemap

根 `/sitemap.xml` 是 **sitemap 索引**，指向 `/zh-cn/sitemap.xml` 与 `/en/sitemap.xml`；
每份子 sitemap 里的 URL 是**该语言的真实地址**（中文那份是 `/posts/...`，不带前缀）。
不需要额外配置。

### 4.4 未翻译的内容

**没有翻译文件的内容，不会出现在该语言的站点里**（实测：只有中文 `about.md` 时，
`/en/about/` 不生成）。这带来一个必须处理的问题：

如果英文站点保留「About」菜单项，它会指向不存在的页面。两种应对，按内容性质选：

- **该页必须有**（关于、栏目页）→ 建英文翻译，保证每个语言站点自洽
- **该页只是暂未翻译**→ 从该语言的菜单里去掉，不要让链接悬空

## 5. 两个项目共用的一套标准

这是本设计的核心：编辑器与博客在下面四件事上用同一套规则，避免各写各的。

| 维度 | 统一标准 |
| --- | --- |
| 语言代码 | BCP 47（`zh-CN`、`en`），两边同一份集合 |
| 资源文件格式 | **JSON**（Hugo 原生支持，浏览器原生支持，不必给前端引 YAML 解析器） |
| 文件名 | `<locale>.json`，与语言代码逐字一致 |
| key 命名 | 点分层级 + 叶节点 `snake_case`，与主题现有风格同构 |

### 5.1 为什么用 JSON 而不是 YAML

主题的翻译文件是 YAML，但那是主题的选择。站点自己的文件用 JSON 的理由：

- 编辑器前端是纯浏览器 JS，读 JSON 无需任何库，YAML 要额外打包解析器（且要进 exe）
- 实测确认 Hugo 同时接受两种格式，且站点 `i18n/<locale>.json` **能覆盖主题的 YAML 同名 key**
  （把 `article.reading_time_title` 改成测试值后，页面确实用了新值）

### 5.2 资源文件的组织

```jsonc
// 博客：i18n/zh-CN.json —— 只放站点自有的与要覆盖的
{
  "home": {
    "intro": "你好，欢迎来到我的博客 👋"
  }
}
```

```jsonc
// 编辑器：static/i18n/zh-CN.json —— 只放编辑器界面的
{
  "action": {
    "save": "保存"
  },
  "media": {
    "pick": "选择文件"
  },
  "error": {
    "no_blog_dir": "还没有设置博客目录，请先在页面上选择"
  }
}
```

**文件里分层，运行时展平。** 落盘按段分组是为了好读好改，而界面查表用的是
`media.pick` 这样的点号键，两者由服务端的 `load_i18n()` 衔接：`/api/i18n/<语言>`
返回的永远是**展平后的点号键**。这一层不能省——客户端拿到的若还是嵌套对象，
每一处 `t()` 都会查不到、整页露出键名。`selftest.py` 的「界面文案接口」一节盯着这件事。

两边**不共用文件**：博客的 key 描述站点内容，编辑器的 key 描述操作界面，
没有一条能同时服务两边。共用的是规则，不是数据。

### 5.3 文案的三种形态

同一个界面上的文字来源不同，处理方式也不同。编辑器的 `loc()` 负责按形态取值：

| 形态 | 长什么样 | 谁产出 | 例 |
| --- | --- | --- | --- |
| 静态文案 | `data-i18n="media.pick"` | 前端标记 | 按钮、标签、占位符 |
| 可本地化提示 | `{key, text, args}` | 后端 | 发布校验的每一条问题 |
| 错误 | `{error, code, args}` | 后端 | `AppError` 抛出的错误 |

后两种都带**中文兜底文本**，作用是翻译漏了也不至于显示成空白——`loc()` 先查
`key` / `error.<code>` 对应的译文，查不到才用兜底。参数里的 `_key` / `_keys`
后缀表示「这个值是语言键」，前端再查一次名字（状态名、动作名、站点字段名），
后端因此不必知道界面在说哪国话。

## 6. 命名规范

### 6.1 语言代码

| 场景 | 写法 | 例 |
| --- | --- | --- |
| Hugo 配置键、URL | 小写 | `[languages.zh-cn]` → `/zh-cn/` |
| `locale`、文件名、前端 | 规范大小写 | `zh-CN.json`、`locale = "zh-CN"` |

只有这两个语言时也要写全区域码（`en` 可省区域，`zh-CN` 不可省——`zh` 与 `zh-TW` 不是一回事）。

### 6.2 key

```
<区域>.<元素>          两层，够用
<区域>.<子区域>.<元素>   区域大时才三层
```

- 区域名用**现有词表**，不新造：主题已有 `global` / `article` / `nav` / `search` /
  `footer` / `list` / `error` / `sharing` / `shortcode` / `a11y` / `author` / `code` /
  `admonition` / `cookie_notice`
- 编辑器自己的区域（`static/i18n/*.json` 的顶层键）：`app` / `header` / `views` /
  `list` / `batch` / `state` / `action` / `field` / `editor` / `media` / `site` /
  `menu` / `setup` / `new` / `publish_check` / `lifecycle` / `result` / `msg` /
  `error` / `check` / `content_lang` / `langs` / `common`
- 叶节点一律 `snake_case`：`scroll_to_top_title`、`no_blog_dir`
- **key 一旦发布不改名**——改名等于所有语言的翻译同时失效

### 6.3 内容文件的语言后缀

| 形态 | 中文（默认，无后缀） | 英文 |
| --- | --- | --- |
| 文章 bundle | `index.md` | `index.en.md` |
| 扁平文章 | `hello-world.md` | `hello-world.en.md` |
| 独立页面 | `about.md` | `about.en.md` |
| 栏目/首页 | `_index.md` | `_index.en.md` |

**默认语言不加后缀**——加了会让中文 URL 多一层，破坏已上线的链接。

## 7. 目录结构

```
blog/
├── hugo.toml                     # [languages] 是语言集合的权威定义
├── i18n/
│   ├── zh-CN.json                # 站点自有 + 覆盖主题
│   └── en.json
├── content/
│   ├── _index.md                 # 首页
│   ├── _index.en.md
│   ├── about.md
│   ├── about.en.md
│   ├── posts/
│   │   ├── _index.md             # 栏目页
│   │   ├── _index.en.md
│   │   └── <slug>/
│   │       ├── index.md          # 正文（默认语言）
│   │       ├── index.en.md       # 英文正文
│   │       └── <媒体文件>         # 两种语言共用
│   └── tags/
│       ├── _index.md
│       └── _index.en.md
└── docs/
    └── i18n.md                   # 本文

blog-editor/
├── static/
│   ├── index.html                # 界面（文案改为 key 引用）
│   └── i18n/
│       ├── zh-CN.json
│       └── en.json
└── app.py
```

**编辑器的 i18n 放在 `static/` 下**是有原因的：打包配置里已有
`datas=[('static', 'static')]`，放这里自动随 exe 分发，不用改 spec 文件。

## 8. 复用约束

1. **不复制主题的翻译。** 主题已提供 97 条中文 / 98 条英文，覆盖了所有内置界面元素。
   站点 `i18n/` 只放两类：主题没有的、以及确实要改写的。
2. **`displayName` 不可省。** 语言切换菜单直接读它，缺了就显示空白。
3. **语言集合只在一处定义。** `hugo.toml` 的 `[languages]` 是权威；编辑器运行时读它
   （`site_language_list()`），不另立一份。语言显示名优先用配置里作者写的 `displayName`。
4. **UI key 与内容 key 不混。** 编辑器界面文案进 `static/i18n/`，
   用户写的内容进 `content/`——前者随 exe 分发，后者是用户数据，生命周期完全不同。
5. **注释不翻译。** 注释是给维护者看的；翻译会让同一段逻辑出现两份说明，必然不同步。
6. **菜单文案不另立副本。** 用页面 title 驱动（3.3），不要在 `[languages.<lang>.menu]`
   里为每种语言重写一遍菜单名。
7. **后端不返回成品文案。** 错误以码传递（`no_blog_dir`），由前端渲染成当前语言。
   后端只保留一份中文兜底，供日志与前端渲染失败时使用。

## 9. 实测依据

以下均在 Hugo 0.165.0 extended + Blowfish 3.6.0 上验证过：

| 结论 | 验证方式 |
| --- | --- |
| 中文 URL 不变、英文在 `/en/` | 加 `[languages]` 后对比构建产物路径 |
| 扁平后缀与 bundle 后缀都支持 | `hello-world.en.md` 与 `markdown-cheatsheet/index.en.md` 均生成正确 URL |
| `hreflang` 双向自动 | 检查中英文章页的 `<link rel="alternate">` |
| `<html lang>` 跟随 `locale` | 中文页 `zh-CN`、英文页 `en` |
| 界面文案自动本地化 | 英文页 `Reading time`、中文页「预计阅读」 |
| 切换组件自动出现 | 产物中 `translation nested-menu` 出现 2 次（桌面 + 移动） |
| 菜单文案可由页面 title 驱动 | 去掉 `name` 后，英文菜单自动变 `Posts` / `About` |
| 站点 JSON 覆盖主题 YAML | 改写 `article.reading_time_title` 后页面用了新值 |
| 未翻译内容不生成 | 无 `about.en.md` 时 `/en/about/` 不存在 |
| sitemap 为索引 + 分语言 | 根 `sitemap.xml` 是 `sitemapindex`，子 sitemap 内 URL 不带前缀 |
| `defaultContentLanguage` 对不上键名会静默丢 `params` | 键名改成 `[languages.zh-CN]` 而默认语言仍是 `"zh-cn"`：日期退回 `September 16, 2026`、语言切换菜单名变空白、`<meta name="description">` 消失，Hugo 无警告 |
| 键名大小写不影响产物 | 键名与 `defaultContentLanguage` 同时改成 `zh-CN`，产物与全小写时 `diff -r` 零差异 |
| `locale` 写错只影响 `hreflang` | 把 `locale` 改成 `zh-cn`：`hreflang` 变 `zh-cn`，中文页主题文案仍是「预计阅读」 |
| 默认语言的内容文件带后缀会顶掉同名页面 | 加 `content/about.zh-cn.md` 后 `/about/` 的标题变成该文件的值，Hugo 无提示 |
| Hugo 会给默认语言生成跳转存根 | `defaultContentLanguageInSubdir = false` 时产物里有 `/zh-cn/index.html`，内容是指向 `/` 的 meta refresh |

## 10. 对标成熟方案：可选思路与取舍

四个环节（界面文案、内容翻译、路由、日期格式）在成熟项目里没有统一答案。下表只写各框架
**官方文档**里写明的内容，「官方未定义」表示那里没有约定、自建时必须自己定规则。

| | Hugo | Astro | Hexo | Docusaurus |
| --- | --- | --- | --- | --- |
| 界面文案 | 站点 `i18n/<语言>.{toml,yaml,json}`；查表顺序 `locale` → 语言键 → 默认语言 → 空串 | **无内置文案表**，官方 recipe 教自建字典 + `t()` | **主题内** `languages/*.yml`，模板用 `__()` | `i18n/<locale>/code.json`，由 `write-translations` 从代码静态提取 |
| 内容翻译 | 文件名后缀（`about.en.md`）或 `contentDir` 目录分叉；**框架级关联**（同路径 basename 或 `translationKey`） | `src/pages/[locale]/` 目录；无自动关联，靠动态路由 | 官方未定义后缀约定，也未定义关联机制 | 内容镜像到 `i18n/<locale>/…`，整篇翻译，无自动关联 |
| 路由 | 默认语言默认在根路径，其他语言 `/<语言键>/`；有 `defaultContentLanguageInSubdir` 开关 | `prefixDefaultLocale` 默认 `false`；非默认语言**总是**带前缀 | 不自动生成多语言路由，要自建 | 默认 locale 定义上不带前缀，其他 `/<locale>/` |
| 日期格式 | 内置 `time.Format` / `lang.FormatNumber`，构建期完成 | recipe 用原生 `toLocaleString(lang)` | 依赖 Moment.js | 只暴露 `calendar`，且声明它不决定显示格式 |
| 切换组件 | 无，只给 `label` 与 `.Translations` 数据 | 无，recipe 自建 | 官方未提及 | 内置 `localeDropdown`，但持久化要自己写 |
| 新增依赖 | 0（构建期，零客户端 JS） | 0（routing 内置） | `hexo-i18n` 随核心；日期依赖 Moment.js | 内置轻量翻译运行时，每个 locale 是独立 SPA |

**对本项目有决定作用的三处分歧**：

1. **内容翻译的关联方式。** 只有 Hugo 把「同一篇的不同语言」做成框架级概念——同路径 basename
   相同即自动关联，也可以用 `translationKey` 强制指定。其余三家都靠目录约定，要自己维护对应关系。
   本项目用 Hugo，于是内容翻译的成本压到最低：加一个 `about.en.md` 就完事，URL 不变，不必建目录分叉。
2. **默认语言要不要进子目录。** Hugo、Astro、Docusaurus 默认都不进，但只有 Hugo 与 Astro 给了开关。
   站点已上线，中文链接是既有事实，所以这里必须 `false`（见 3.1）。
3. **界面文案表放在哪。** Hugo 放站点、Hexo 放主题内、Docusaurus 统一到 `i18n/<locale>/`、Astro
   没有官方机制。编辑器不在 Hugo 里，用不了 `i18n/`，所以走自建运行时；格式选 JSON 的理由见 5.1。

**逐环节的选型结论**：

| 环节 | 选了 | 依据 |
| --- | --- | --- |
| 博客界面文案 | Hugo 原生 `i18n/` + 主题自带翻译 | 零依赖、零客户端 JS；主题已覆盖 36 种语言 |
| 博客内容翻译 | 文件名后缀 | Hugo 的框架级关联，URL 不变，且是编辑器 bundle 约定的自然延伸 |
| 博客路由 | 默认语言留在根路径 | 既有链接不能搬家 |
| 博客日期格式 | `site.Language.Params.dateFormat` | 主题已按语言取值，不必自己写格式化 |
| 博客切换入口 | 主题内置组件 | 不必自写组件，也不必自维护持久化 |
| 编辑器界面文案 | 自建运行时 + 两份 JSON | 编辑器不在 Hugo 里；JSON 浏览器原生可读，不必引 YAML 解析器 |
| 编辑器内容语言 | 显式 `lang` 参数 | 后端不必猜；单语言站点行为不变 |
| 编辑器日期 | 不本地化 | 编辑器只写 `date` 字段，格式化是 Hugo 的事 |

## 11. 依赖、体积与代码量

### 11.1 新增依赖：两边都是 0

| 项目 | 新增依赖 | 说明 |
| --- | --- | --- |
| `blog` | 无 | Hugo 是单二进制，`i18n/` 是它自带能力；主题的 36 份翻译已在 `themes/blowfish/i18n/` 内，**不复制到站点** |
| `blog-editor` | 无 | 标准库 + 原本就有的 PyYAML；文案表用 JSON，前端不需要解析器 |

没有引入任何 i18n 库，也就没有随之而来的版本升级、安全公告与传递依赖。
主题翻译文件留在 vendor 目录里，升级主题时跟着走，不需要人工同步。

### 11.2 体积

| 项 | 量 |
| --- | --- |
| 编辑器文案表 | `zh-CN.json` 17.8 KB + `en.json` 18.3 KB（301 条 × 2） |
| 编辑器 i18n 运行时 | 83 行 JS，占 `index.html` 2458 行的 3.4% |
| 站点文案表 | `i18n/zh-CN.json` 52 字节（1 条） |
| 博客内容 | 8 个英文文件，与中文一一对应 |
| 客户端 JS | 新增 0 —— 博客的本地化全在构建期完成 |

exe 约 9.1 MB，其中 i18n 的增量只有两份 JSON；没有新增运行时组件，也没有多出解压后的文件。

### 11.3 代码量分配

| 模块 | 规模 | 为什么是这个量 |
| --- | --- | --- |
| `hugo.toml` 的 `[languages]` | 29 行 | 语言集合 + 每语言的标题/简介/日期格式 |
| 博客内容 | 8 个英文文件 | 与中文一一对应，**不加逻辑** |
| `tools/check.py` 的语言检查 | 71 行 | 拦四类不报错的错（见 §1、§3.3、§6.3） |
| `tools/verify_i18n.py` | 131 行 / 29 项 | 产物验证，含「中文 URL 不搬家」基线 |
| 编辑器文案表 | 301 条 × 2 | 数据不是代码，加语言是纯新增；语言名单另在 `LANGUAGES` |
| 编辑器前端运行时 | 83 行 / 10 个函数 | `t()` / `loc()` / `locArgs()` / `refreshTexts()` 等 |
| 编辑器接线 | 172 处 `t()`、8 处 `loc()`、41 处 `data-i18n` | 逐处替换，无法自动化；JS 里中文字面量为 0 |
| 编辑器后端 | 7 个单元共 122 行；65 处带码 `raise` / `fail`；20 处 `msg()` | 错误只传码，后端不存成品文案 |
| `check_i18n.py` | 150 行 / 10 项 | 两份表对齐 + key 与错误码交叉校验 |

**分布的特征：代码集中在检查（约 340 行）而不是运行时（83 行）。** 这是刻意的——
i18n 的失败形态几乎都是静默的（文案不换、链接悬空、`hreflang` 变样），
所以回报最高的投入是「让它报错」，而不是「让它更聪明」。

### 11.4 刻意没写的东西

| 没做 | 理由 |
| --- | --- |
| 语言切换组件 | 主题已内置（含持久化），自写只会多一份要维护的 UI |
| 翻译提取 / 同步工具链 | key 是手写的，301 条的量级不值得引入提取器；漏了由 `check_i18n.py` 查 |
| 运行时的多级文案回退 | 后端每条提示都带中文兜底，前端只查一次，不需要回退链 |
| 日期库 | Hugo 内置按语言格式化，编辑器不显示日期 |
| 内容的机器翻译 | 翻译由人写（见 §13） |

## 12. 扩展到 N 种语言

**语言数量不构成架构约束。** 界面文案是一份文件一种语言，内容是一篇一种语言，
落点都不随语言数量变化——2 种和 36 种的结构完全一样。

### 12.1 差在哪：只差翻译，不差代码

博客侧加语言**不改代码**：语言集合在 `hugo.toml`，模板读 `.AllTranslations` / `.Translations`。
编辑器侧原本有三处写死的名单（`app.py` 的 `LANGUAGES`、`check_i18n.py` 的 `LANGS`、
`verify_i18n.py` 的逐语言断言），**现已全部改为从事实派生**：

| 位置 | 现状 |
| --- | --- |
| `app.py` 的 `interface_languages()` | 扫描 `static/i18n/*.json`——目录里有什么语言，`/api/i18n` 就收敛到什么语言 |
| `check_i18n.py` 的 `LANGS` | 同样从目录派生，每份表都与基线 `zh-CN` 对齐 |
| `tools/verify_i18n.py` | 语言与期望 URL 从 `hugo.toml` 和内容文件的语言后缀推导，逐语言自动核对 |

内容语言同样动态：`site_languages()` 读 `hugo.toml`，博客加语言后编辑器的语言条自动多一项。

所以 §12.4 的扩展流程里**没有任何「改代码」步骤**——剩下的都是放文件和跑检查。

### 12.2 语言资源放在哪

四处落点，互相独立：

| 资源 | 落点 | 命名 | 谁读 |
| --- | --- | --- | --- |
| 博客界面文案（站点自有 / 覆盖主题） | `i18n/<locale>.json` | BCP 47 规范大小写 | Hugo，构建期 |
| 博客主题文案 | `themes/blowfish/i18n/<locale>.yaml`（vendor，36 种现成） | 同上 | Hugo，构建期 |
| 博客内容 | 内容文件的语言后缀，如 `index.ja.md` | 语言**键名**，全小写 | Hugo，构建期 |
| 编辑器界面文案 | `static/i18n/<代码>.json` | BCP 47，文件名即语言代码 | 编辑器后端，经 `/api/i18n/<码>` |

三条组织原则：

- **一种语言 = 一份文件**，不做目录分叉。加语言是「新增文件」，不是「在每处插一个分支」。
- **分层只到段**（`media.pick`），再深一级就没人维护了。文件里分层是为了好读，运行时展平成点号键（§5.2）。
- **两边不共用条目**（§5.2）。共用的是规则，不是数据。

### 12.3 语言怎么选、怎么切

两条链路互不相干，因为两个产品的形态不同。

博客——语言进 URL，切换在构建期就定死：

```
URL 前缀 ──→ 静态 HTML（语言已固定）
              ├─ <html lang> / hreflang ← locale
              ├─ 切换入口 = 主题组件，列 .AllTranslations
              └─ 持久化 = 主题写 blowfish_preferred_language
```

编辑器——语言是用户偏好，不进 URL：

```
localStorage「blog-editor.language」
  └─ 无记忆值时猜 navigator.languages，收敛到 LANGUAGES 里的一个
       └─ GET /api/i18n/<码> → 展平的点号键表
            └─ 换表 → 重刷 data-i18n 标记 + 重刷动态区域
```

**为什么不一样**：博客的 URL 标识内容（`/en/posts/x/` 是可分享的地址），语言必须进 URL；
编辑器是本地单页工具，地址没有分享意义，语言属于偏好，所以走 `localStorage`。

### 12.4 新增一种语言的流程

以日语为例。**先博客后编辑器**——编辑器的内容语言自动跟随 `hugo.toml`。

博客：

| 步 | 动作 | 必需 |
| --- | --- | --- |
| 1 | `hugo.toml` 加 `[languages.ja]`：`locale = "ja"`、`title`、`weight`、`params.displayName`、`params.dateFormat` | 是 |
| 2 | 建内容 `content/posts/<slug>/index.ja.md`；不建则该语言没有这个页面（§4.4） | 否 |
| 3 | 站点自有文案写 `i18n/ja.json`；主题已有 `themes/blowfish/i18n/ja.yaml`，不用动 | 否 |
| 4 | `hugo --gc --minify` → `python tools/verify_i18n.py` → `python tools/check.py`（语言与期望 URL 自动推导） | 是 |

编辑器：

| 步 | 动作 | 必需 |
| --- | --- | --- |
| 1 | 加 `static/i18n/ja.json`：与 `zh-CN.json` 逐条同 key，含 `langs.ja: "日本語"` | 是 |
| 2 | 两份旧表各补 `langs.ja`（key 集合必须一致） | 是 |
| 3 | 重建 `dist/blog-editor.exe`——文案表打进 exe | 是 |
| 4 | `python check_i18n.py` → `python selftest.py` | 是 |

语言选择器会自动多出日语（选项由文案表的 `langs` 段驱动）；`guessLanguage()` 把浏览器
语言原样交给后端收敛，认不出的落回默认语言，不需要改前端。

### 12.5 成熟项目的常见思路

左列是成熟 i18n 方案里的标准做法，右列是本项目的取舍。取舍依据都是**「这个风险现在存在吗」**——
不存在的能力不预先建设（§11.4 同理）。

| 思路 | 成熟项目怎么做 | 本项目 |
| --- | --- | --- |
| 消息格式 | ICU MessageFormat：`{n, plural, one {...} other {...}}`，把复数、性别、选择写进文案 | 只做 `{name}` 位置插值。中文无复数变化，英文的 `one/other` 也只是两条；等真加复数语言再引 |
| 复数 | CLDR plural categories（俄语 3 类、阿拉伯语 6 类） | 不做。要做时用浏览器原生 `Intl.PluralRules`，不必装库 |
| 日期 / 数字 | `Intl.DateTimeFormat` / `NumberFormat` | 博客交给 Hugo 的 `dateFormat`（构建期，零客户端 JS）；编辑器不显示日期 |
| 回退链 | 多级：`ja-JP` → `ja` → `en` → 默认 | 单级：缺条目落到该条目自带的中文兜底（§5.3）。后端每条提示都带兜底，不需要链 |
| 语言协商 | `Accept-Language` 加权做内容协商 | 博客由 URL 决定（静态站没有协商余地）；编辑器猜一次就存进 `localStorage` |
| 文案提取 | 从代码静态提取 key（Docusaurus 的 `write-translations`、gettext 的 `xgettext`） | 不提取。301 条手写，改由 `check_i18n.py` 双向查：代码引用但表里没有、表里有但没人用 |
| key 的上下文 | gettext 的 `msgctxt`，同一句话在不同场景用不同译文 | 不需要。key 自带段名（`list.section_published`），场景已经在 key 里 |
| 伪本地化 | 假语言（`[!! Ţéšţ !!]`）跑一遍，看有没有漏网的硬编码文案 | 用静态检查代替：扫 JS 里的中文字符串字面量，当前为 0 |
| RTL | `dir="rtl"` + CSS 逻辑属性（`margin-inline-start`） | 不做。主题与编辑器都按 LTR 写，加阿拉伯语 / 希伯来语要另算 CSS 成本 |
| 翻译工作流 | TMS（Crowdin / Transifex）+ PO 文件往返 | 不做。人手改 JSON，git 即版本管理 |

### 12.6 注意事项

1. **语言代码只有一个真相，但分两种写法**：`locale` 用规范大小写、键名全小写（§1）。
   写混了不报错——`defaultContentLanguage` 对不上键名会整块丢 `params`，`locale` 写错只影响 `hreflang`。
2. **界面语言与内容语言是两个维度**（§3.4）。「编辑器界面多一种语言」不等于「文章多一个语言版本」，
   两者要加的东西完全不同。
3. **i18n 的失败几乎都是静默的**：文案不换、链接悬空、`hreflang` 变样，构建都不报错。
   所以 §11.3 里检查代码占大头——「让它报错」比「让它更聪明」回报高。
4. **界面文案是有限集合，内容是无限增长的**。界面加一种语言一次到位；内容每写一篇都要决定翻不翻。
   这是长期成本所在，也是为什么内容翻译的关联方式必须便宜（§10 第一条分歧）。

## 13. 边界

- **主题自身的界面文案**：改主题要复制模板到站点根 `layouts/`（项目硬约束），
  成本高于收益。主题已支持 36 种语言，够用。
- **URL 结构的改动**：不加 `defaultContentLanguageInSubdir`，
  中文地址保持现状。
- **内容的机器翻译**：翻译由人写，方案只提供放置位置与匹配规则。
- **RSS / JSON 搜索索引的多语言**：Hugo 会自动为每个语言生成，
  站点搜索的跨语言行为不在本次范围。
