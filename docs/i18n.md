# 国际化（i18n）规范

覆盖两个项目：`blog`（Hugo 静态站）与 `blog-editor`（内容编辑器）。
本文描述**当前的实现**：两边各自怎么组织文案、语言怎么切换、构建阶段怎么按语言出页。
文中标注「实测」的结论都来自本仓库实际构建或接口调用的输出。

---

## 0. 范围

| 项目 | 国际化的部分 |
| --- | --- |
| `blog` | 站点界面文案、文章/页面/栏目页内容、站点设置、导航菜单 |
| `blog-editor` | 编辑器界面文案、后端返回给界面的消息、编辑器的内容读写 |

两边的**语言代码、key 命名、资源文件格式**共用同一套标准（第 5 节），
但**翻译文件各自独立**——它们描述的是不同的东西，没有可共用的条目。

---

## 1. 语言集合

| 项 | 取值 |
| --- | --- |
| 语言代码标准 | **BCP 47**（`zh-CN`、`en`），与 `hugo.toml` 的 `locale` 一致 |
| Hugo 的 `lang` 键 | **全小写**（`zh-cn`、`en`），只用于 URL 与配置键名 |
| 默认语言 | `zh-cn` |
| 起步语言 | `zh-cn`（默认）+ `en` |
| 扩展方式 | 博客：在 `[languages]` 加一块 + 建对应内容文件；编辑器：加一份 `static/i18n/<代码>.json`。两边都**不改任何模板或代码** |

**为什么是这两个**：站点内容、README、编辑器界面当前全是中文，作者是中文母语者，
英文是覆盖面最广的第二语言。数量本身不构成架构约束——方案按 N 种语言设计。

**大小写的分工不能混**（实测确认）：

- `locale = "zh-CN"` → 决定 `<html lang>`、`hreflang`、以及**匹配主题的 `i18n/zh-CN.yaml`**
- `lang = "zh-cn"`（即 `[languages.zh-cn]` 的键名）→ 决定 URL 前缀 `/zh-cn/` 与配置键名

写成 `locale = "zh-cn"` 会让 `hreflang` 输出不规范；写成 `[languages.zh-CN]` 会让 URL 变成 `/zh-CN/`。

## 2. 需要国际化的内容

### 2.1 博客：内容

| 类型 | 位置 | 翻译方式 |
| --- | --- | --- |
| 文章 | `content/posts/<slug>/index.md` | 同目录 `index.<lang>.md` |
| 独立页面 | `content/about.md` | `about.<lang>.md` |
| 栏目页 | `content/posts/_index.md` | `_index.<lang>.md` |
| 首页 | `content/_index.md` | `_index.<lang>.md` |
| 分类/标签/合集页 | `content/tags/_index.md` 等 | `_index.<lang>.md` |

文章用 **page bundle + 语言后缀**（`index.md` / `index.en.md`），媒体文件两份共用，
URL 不变。这与编辑器现有的 bundle 约定一致，是它的自然延伸。

**taxonomy 页要单独建**：`tags`、`categories`、`series` 三个 taxonomy 列表页
默认由 Hugo 自动生成标题（中文站点会显示成英文的 `Tags`）。要本地化就必须
建 `content/tags/_index.md`（中文 title）+ `_index.en.md`（英文 title），
菜单文案才会跟着对（见 3.3）。

### 2.2 博客：界面与配置

| 类型 | 位置 | 说明 |
| --- | --- | --- |
| 主题界面文案 | 主题自带 `i18n/*.yaml`（35 种语言，中文 97 条） | **不复制**，站点按需覆盖 |
| 站点自定义文案 | `i18n/<locale>.json` | 新增；也可覆盖主题同名 key |
| 站点标题/简介 | `hugo.toml` 的 `[languages.<lang>]` 与 `.params` | 每种语言一份 |
| 导航菜单文案 | **不写死**，由页面 title 驱动 | 见 3.3 |
| 站点设置（作者、社交链接） | `hugo.toml` 的 `[languages.<lang>.params]` | 不随语言变的可留在顶层 |

### 2.3 编辑器

| 类型 | 位置 | 数量（实测） |
| --- | --- | --- |
| 界面静态文案（HTML） | `static/index.html` | 11 个 `placeholder` + 页面区块 |
| 界面动态文案（JS） | `static/index.html` 的 `<script>` | 38 处 `toast()`、7 处 `confirm()` |
| 后端消息 | `app.py` | 21 处 `raise`、12 处 `fail()`、3 处 `fail_quietly()` |
| 内容读写 | `app.py` 的文件路径逻辑 | 支持 `index.<lang>.md` |

**明确不进 i18n 的**：代码注释与 docstring（`app.py` 约 112 行、`index.html` 约 112 行）、
`_log()` 日志（开发者看的，且中文更利于排查）。这些是给维护者读的，翻译它们只会增加维护面。

## 3. 语言切换与默认语言

### 3.1 博客：URL 结构

```toml
defaultContentLanguage = "zh-cn"
defaultContentLanguageInSubdir = false   # 中文留在根路径
```

产物（实测）：

```
/posts/hello-world/          中文，URL 与上线现状完全一致
/en/posts/hello-world/       英文
/about/  /en/about/
```

**`defaultContentLanguageInSubdir` 必须是 `false`**：站点已上线，
`baseURL` 下的中文链接是既有事实，不能因为加语言而整体搬家。

副作用（实测）：Hugo 会自动生成 `/zh-cn/index.html`——一个指向 `/` 的
`meta refresh` 重定向页，以及 `/zh-cn/sitemap.xml`。前者是 Hugo 的固有行为，
canonical 指向根路径，无害；后者是 sitemap 索引的组成部分（见 4.3），不是冗余。

### 3.2 博客：切换入口

**不用自己写组件**——主题已内置，无需任何配置：

- `layouts/partials/header/components/translations.html` 在 `.IsTranslated` 为真时
  自动出现在桌面菜单与移动菜单里，列出 `.AllTranslations`
- 每项显示的是 `[languages.<lang>.params] displayName`，**这个字段必填**，否则菜单项空白
- `head.html` 自动输出双向 `hreflang`（用 `locale` 值）
- 可选：`params.languageRedirect` 启用按浏览器语言/上次选择自动跳转
  （`storageKey` 默认 `blowfish_preferred_language`）

### 3.3 导航菜单：文案的单一来源

菜单项现在写成 `name = "文章"`，这是**页面标题的副本**——
`content/posts/_index.md` 的 `title` 已经是"文章"。两处描述同一件事，加语言时必然不同步。

主题模板取的是 `{{ .Name | markdownify }}`，不做 i18n。但 Hugo 在菜单项
**没有显式 `name`** 时用 `pageRef` 指向页面的 title 当菜单文案。所以：

```toml
[[menu.main]]
  pageRef = "posts"      # 不要 name
  weight = 10
```

实测效果：中文菜单「文章 / 关于」，英文菜单自动变成「Posts / About」。
**菜单文案的来源从此只有一处——页面自己的 title。**

### 3.4 编辑器：语言设置

编辑器里有**两个互不相干的「语言」**，不要混：

| 维度 | 含义 | 入口 | 取值来源 |
| --- | --- | --- | --- |
| 界面语言 | 编辑器自己的按钮、提示用哪种语言 | 页头语言选择器 | 编辑器自带的文案表（见 §5） |
| 内容语言 | 正在编辑的是哪一版文章 | 编辑器顶部的语言条 | 站点配置 `[languages]` |

界面语言：

| 项 | 约定 |
| --- | --- |
| 默认语言 | `zh-CN` |
| 记忆方式 | `localStorage`，键名 `blog-editor.language`（与主题的 `blowfish_preferred_language` 区分） |
| 首次访问 | 无记忆值时取浏览器语言，认不出的一律收敛到 `zh-CN` |
| 取文案 | `GET /api/i18n/<语言>`，返回**展平成点号键**的文案表 |

内容语言：

| 项 | 约定 |
| --- | --- |
| 传递方式 | 显式参数——`GET` 走 `?lang=`，`POST` 走请求体的 `lang` 字段 |
| 单语言站点 | 不传，也不显示语言条；行为与没有多语言时完全一致 |
| 未配置的语言 | 后端返回 `unknown_lang` 错误，不悄悄退回默认语言 |
| 站点没配多语言时 | `lang` 一律按 `None` 处理，字段路径落在配置顶层 |

后端只把语言用于**选文案和选文件**，不参与任何业务判断——语言不影响文章状态的算法。

## 4. 构建阶段的语言输出

### 4.1 每个语言独立渲染

Hugo 按 `[languages]` 逐语言渲染整站。内容文件的匹配规则是**文件名去掉语言后缀后相同**，
即 `hello-world.md` ↔ `hello-world.en.md`，bundle 则是 `index.md` ↔ `index.en.md`。
媒体文件不参与匹配，两份内容共用同目录的图片/视频。

### 4.2 自动产出的语言标记（实测）

| 产物 | 中文页 | 英文页 |
| --- | --- | --- |
| `<html lang>` | `zh-CN` | `en` |
| `hreflang` | 同时输出 `zh-CN` 与 `en` 两条，互相指向 | 同左 |

两边的 `hreflang` 是同一对，这是搜索引擎识别翻译关系的依据，无需手工维护。

### 4.3 sitemap

根 `/sitemap.xml` 是 **sitemap 索引**，指向 `/zh-cn/sitemap.xml` 与 `/en/sitemap.xml`；
每份子 sitemap 里的 URL 是**该语言的真实地址**（中文那份是 `/posts/...`，不带前缀）。
不需要额外配置。

### 4.4 未翻译的内容

**没有翻译文件的内容，不会出现在该语言的站点里**（实测：只有中文 `about.md` 时，
`/en/about/` 不生成）。这带来一个必须处理的问题：

如果英文站点保留「About」菜单项，它会指向不存在的页面。两种应对，按内容性质选：

- **该页必须有**（关于、栏目页）→ 建英文翻译，保证每个语言站点自洽
- **该页只是暂未翻译**→ 从该语言的菜单里去掉，不要让链接悬空

## 5. 两个项目共用的一套标准

这是本设计的核心：编辑器与博客在下面四件事上用同一套规则，避免各写各的。

| 维度 | 统一标准 |
| --- | --- |
| 语言代码 | BCP 47（`zh-CN`、`en`），两边同一份集合 |
| 资源文件格式 | **JSON**（Hugo 原生支持，浏览器原生支持，不必给前端引 YAML 解析器） |
| 文件名 | `<locale>.json`，与语言代码逐字一致 |
| key 命名 | 点分层级 + 叶节点 `snake_case`，与主题现有风格同构 |

### 5.1 为什么用 JSON 而不是 YAML

主题的翻译文件是 YAML，但那是主题的选择。站点自己的文件用 JSON 的理由：

- 编辑器前端是纯浏览器 JS，读 JSON 无需任何库，YAML 要额外打包解析器（且要进 exe）
- 实测确认 Hugo 同时接受两种格式，且站点 `i18n/<locale>.json` **能覆盖主题的 YAML 同名 key**
  （把 `article.reading_time_title` 改成测试值后，页面确实用了新值）

### 5.2 资源文件的组织

```jsonc
// 博客：i18n/zh-CN.json —— 只放站点自有的与要覆盖的
{
  "home": {
    "intro": "你好，欢迎来到我的博客 👋"
  }
}
```

```jsonc
// 编辑器：static/i18n/zh-CN.json —— 只放编辑器界面的
{
  "action": {
    "save": "保存"
  },
  "media": {
    "pick": "选择文件"
  },
  "error": {
    "no_blog_dir": "还没有设置博客目录，请先在页面上选择"
  }
}
```

**文件里分层，运行时展平。** 落盘按段分组是为了好读好改，而界面查表用的是
`media.pick` 这样的点号键，两者由服务端的 `load_i18n()` 衔接：`/api/i18n/<语言>`
返回的永远是**展平后的点号键**。这一层不能省——客户端拿到的若还是嵌套对象，
每一处 `t()` 都会查不到、整页露出键名。`selftest.py` 的「界面文案接口」一节盯着这件事。

两边**不共用文件**：博客的 key 描述站点内容，编辑器的 key 描述操作界面，
没有一条能同时服务两边。共用的是规则，不是数据。

### 5.3 文案的三种形态

同一个界面上的文字来源不同，处理方式也不同。编辑器的 `loc()` 负责按形态取值：

| 形态 | 长什么样 | 谁产出 | 例 |
| --- | --- | --- | --- |
| 静态文案 | `data-i18n="media.pick"` | 前端标记 | 按钮、标签、占位符 |
| 可本地化提示 | `{key, text, args}` | 后端 | 发布校验的每一条问题 |
| 错误 | `{error, code, args}` | 后端 | `AppError` 抛出的错误 |

后两种都带**中文兜底文本**，作用是翻译漏了也不至于显示成空白——`loc()` 先查
`key` / `error.<code>` 对应的译文，查不到才用兜底。参数里的 `_key` / `_keys`
后缀表示「这个值是语言键」，前端再查一次名字（状态名、动作名、站点字段名），
后端因此不必知道界面在说哪国话。

## 6. 命名规范

### 6.1 语言代码

| 场景 | 写法 | 例 |
| --- | --- | --- |
| Hugo 配置键、URL | 小写 | `[languages.zh-cn]` → `/zh-cn/` |
| `locale`、文件名、前端 | 规范大小写 | `zh-CN.json`、`locale = "zh-CN"` |

只有这两个语言时也要写全区域码（`en` 可省区域，`zh-CN` 不可省——`zh` 与 `zh-TW` 不是一回事）。

### 6.2 key

```
<区域>.<元素>          两层，够用
<区域>.<子区域>.<元素>   区域大时才三层
```

- 区域名用**现有词表**，不新造：主题已有 `global` / `article` / `nav` / `search` /
  `footer` / `list` / `error` / `sharing` / `shortcode` / `a11y` / `author` / `code` /
  `admonition` / `cookie_notice`
- 编辑器自己的区域（`static/i18n/*.json` 的顶层键）：`app` / `header` / `views` /
  `list` / `batch` / `state` / `action` / `field` / `editor` / `media` / `site` /
  `menu` / `setup` / `new` / `publish_check` / `lifecycle` / `result` / `msg` /
  `error` / `check` / `content_lang` / `langs` / `common`
- 叶节点一律 `snake_case`：`scroll_to_top_title`、`no_blog_dir`
- **key 一旦发布不改名**——改名等于所有语言的翻译同时失效

### 6.3 内容文件的语言后缀

| 形态 | 中文（默认，无后缀） | 英文 |
| --- | --- | --- |
| 文章 bundle | `index.md` | `index.en.md` |
| 扁平文章 | `hello-world.md` | `hello-world.en.md` |
| 独立页面 | `about.md` | `about.en.md` |
| 栏目/首页 | `_index.md` | `_index.en.md` |

**默认语言不加后缀**——加了会让中文 URL 多一层，破坏已上线的链接。

## 7. 目录结构

```
blog/
├── hugo.toml                     # [languages] 是语言集合的权威定义
├── i18n/
│   ├── zh-CN.json                # 站点自有 + 覆盖主题
│   └── en.json
├── content/
│   ├── _index.md                 # 首页
│   ├── _index.en.md
│   ├── about.md
│   ├── about.en.md
│   ├── posts/
│   │   ├── _index.md             # 栏目页
│   │   ├── _index.en.md
│   │   └── <slug>/
│   │       ├── index.md          # 正文（默认语言）
│   │       ├── index.en.md       # 英文正文
│   │       └── <媒体文件>         # 两种语言共用
│   └── tags/
│       ├── _index.md
│       └── _index.en.md
└── docs/
    └── i18n.md                   # 本文

blog-editor/
├── static/
│   ├── index.html                # 界面（文案改为 key 引用）
│   └── i18n/
│       ├── zh-CN.json
│       └── en.json
└── app.py
```

**编辑器的 i18n 放在 `static/` 下**是有原因的：打包配置里已有
`datas=[('static', 'static')]`，放这里自动随 exe 分发，不用改 spec 文件。

## 8. 复用约束

1. **不复制主题的翻译。** 主题已提供 97 条中文 / 98 条英文，覆盖了所有内置界面元素。
   站点 `i18n/` 只放两类：主题没有的、以及确实要改写的。
2. **`displayName` 不可省。** 语言切换菜单直接读它，缺了就显示空白。
3. **语言集合只在一处定义。** `hugo.toml` 的 `[languages]` 是权威；编辑器运行时读它
   （`site_language_list()`），不另立一份。语言显示名优先用配置里作者写的 `displayName`。
4. **UI key 与内容 key 不混。** 编辑器界面文案进 `static/i18n/`，
   用户写的内容进 `content/`——前者随 exe 分发，后者是用户数据，生命周期完全不同。
5. **注释不翻译。** 注释是给维护者看的；翻译会让同一段逻辑出现两份说明，必然不同步。
6. **菜单文案不另立副本。** 用页面 title 驱动（3.3），不要在 `[languages.<lang>.menu]`
   里为每种语言重写一遍菜单名。
7. **后端不返回成品文案。** 错误以码传递（`no_blog_dir`），由前端渲染成当前语言。
   后端只保留一份中文兜底，供日志与前端渲染失败时使用。

## 9. 实测依据

以下均在 Hugo 0.165.0 extended + Blowfish 3.6.0 上验证过：

| 结论 | 验证方式 |
| --- | --- |
| 中文 URL 不变、英文在 `/en/` | 加 `[languages]` 后对比构建产物路径 |
| 扁平后缀与 bundle 后缀都支持 | `hello-world.en.md` 与 `markdown-cheatsheet/index.en.md` 均生成正确 URL |
| `hreflang` 双向自动 | 检查中英文章页的 `<link rel="alternate">` |
| `<html lang>` 跟随 `locale` | 中文页 `zh-CN`、英文页 `en` |
| 界面文案自动本地化 | 英文页 `Reading time`、中文页「预计阅读」 |
| 切换组件自动出现 | 产物中 `translation nested-menu` 出现 2 次（桌面 + 移动） |
| 菜单文案可由页面 title 驱动 | 去掉 `name` 后，英文菜单自动变 `Posts` / `About` |
| 站点 JSON 覆盖主题 YAML | 改写 `article.reading_time_title` 后页面用了新值 |
| 未翻译内容不生成 | 无 `about.en.md` 时 `/en/about/` 不存在 |
| sitemap 为索引 + 分语言 | 根 `sitemap.xml` 是 `sitemapindex`，子 sitemap 内 URL 不带前缀 |

## 10. 边界

- **主题自身的界面文案**：改主题要复制模板到站点根 `layouts/`（项目硬约束），
  成本高于收益。主题已支持 35 种语言，够用。
- **URL 结构的改动**：不加 `defaultContentLanguageInSubdir`，
  中文地址保持现状。
